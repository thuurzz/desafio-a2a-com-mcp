# Tasks

## 1. Estrutura do projeto e cliente MCP (~55 min)

- [ ] 1.1 Criar `agente/pyproject.toml` com `mcp>=2.3,<3` e o layout `agente/models/`, `agente/controllers/`, `agente/views/` (pacotes com `__init__.py`), processo separado do servidor MCP, URL default `http://127.0.0.1:7301/mcp` parametrizável por env. **Verificação:** `.venv/bin/python -c "import agente.models, agente.controllers, agente.views"` sai sem erro e `grep -q 'mcp>=' agente/pyproject.toml`.
- [ ] 1.2 Confirmar as assinaturas reais dos tipos de wire no SDK instalado (`ListToolsResult`, `Tool`, `ReadResourceResult`, `CallToolResult`, `InputRequiredResult`, `InputResponses`, `StructuredContent`, `TextContent`) antes de escrever o transporte. **Verificação:** `.venv/bin/python -c "import mcp.types as t; print([n for n in dir(t) if 'ListTools' in n or 'InputRequired' in n or 'ReadResource' in n or 'CallTool' in n])"` lista os nomes esperados do `docs/sdk-mcp-2.3.0.md`.
- [ ] 1.3 Implementar o transporte fino em `agente/views/` (cliente MCP Streamable HTTP): montar envelope JSON-RPC, `_meta` completo e headers `MCP-Protocol-Version`/`Mcp-Method`/`Mcp-Name`, e desserializar com `mcp.types`. **Verificação:** um `tools/list` manual com `curl -s -X POST http://127.0.0.1:7301/mcp -H 'Content-Type: application/json' -H 'MCP-Protocol-Version: 2026-07-28' -H 'Mcp-Method: tools/list' -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientCapabilities":{"elicitation":{"form":{}}}}}}'` devolve `200` com as três tools.

## 2. Descoberta, resource e metadados (~60 min)

- [ ] 2.1 Implementar `tools/list` em runtime no cliente (sem catálogo hardcoded) e `resources/read` de `politica://uso`, extraindo a versão da primeira linha (`versao: <valor>`). **Verificação:** `.venv/bin/python -c "from agente.controllers import descobrir; print(descobrir())"` (ou o entrypoint) imprime as três tools e a versão `2026-11-01`.
- [ ] 2.2 Garantir que todo request MCP emitido carrega `_meta` com `protocolVersion`, `clientCapabilities` (`{"elicitation":{"form":{}}}`), `clientInfo` e o `traceparent` propagado (trace-id preservado, span-id novo). **Verificação:** subir o servidor com stderr em `/tmp/servidor-mcp.log`, rodar o script com `traceparent=00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01` e conferir `grep -q '4bf92f3577b34da6a3ce929d0e0e4736' /tmp/servidor-mcp.log`.
- [ ] 2.3 Espelhar os headers `Mcp-Name` em `tools/call` (nome da tool) e `resources/read` (URI), além de `MCP-Protocol-Version`/`Mcp-Method` em todo request. **Verificação:** no stderr do servidor, os requests do agente aparecem com o método correto e, para `resources/read`, o nome `politica://uso` (o servidor da fase 2 recusa header que não bate com o corpo com `-32020`; ausência de `-32020` confirma o espelhamento).

## 3. Interpretação do pedido e resultado tipado (~60 min)

- [ ] 3.1 Implementar em `agente/controllers/` o parser determinístico do pedido fixo `reservar sala=<id> inicio=<iso8601> fim=<iso8601> responsavel=<nome>` (sem LLM), devolvendo um `Pedido` tipado. **Verificação:** `.venv/bin/python -c "from agente.controllers import interpretar_pedido; print(interpretar_pedido('reservar sala=sala-garagem inicio=2026-11-03T14:00:00-03:00 fim=2026-11-03T15:00:00-03:00 responsavel=Marty'))"` imprime os quatro campos corretos.
- [ ] 3.2 Implementar o resultado tipado em `agente/models/` (`completado`/`pausado`/`falhou`) e o `executar_pedido(texto, traceparent)` que chama `reservar_sala` e traduz `complete`→criada (com `politica`), `input_required`→pausada (guardando `inputRequests` e `requestState` crus) e `isError`→falha (mensagem exata). **Verificação:** `.venv/bin/python` chamando `executar_pedido('reservar sala=sala-porao inicio=2026-11-03T09:00:00-03:00 fim=2026-11-03T10:00:00-03:00 responsavel=Doc')` devolve um resultado `completado` com `politica == '2026-11-01'`.
- [ ] 3.3 Verificar o caminho de falha: pedido de sala inexistente devolve `falhou` com a mensagem exata da tool. **Verificação:** `executar_pedido('reservar sala=sala-delorean inicio=2026-11-03T09:00:00-03:00 fim=2026-11-03T10:00:00-03:00 responsavel=Doc')` devolve `falhou` com `Sala inexistente: sala-delorean` na mensagem.

## 4. Pausa e continuação (MRTR como cliente) (~60 min)

- [ ] 4.1 Confirmar que o `executar_pedido` de um conflito devolve `pausado`, guardando o `inputRequests` e o `requestState` **opacos** (nenhum campo é aberto além da chave única). **Verificação:** `executar_pedido('reservar sala=sala-garagem inicio=2026-11-03T14:00:00-03:00 fim=2026-11-03T15:00:00-03:00 responsavel=Marty')` devolve `pausado` com `requestState` presente e o `inputRequests` cru.
- [ ] 4.2 Implementar `continuar(task, escolha)` que refaz o `tools/call` com **id novo**, `inputResponses` com a **mesma chave** do `inputRequests` (`action=accept`, `content.sala=escolha`) e o `requestState` ecoado byte a byte. **Verificação:** continuar a pausa de 4.1 com `escolha='sala-fusca'` devolve `completado` com `sala == 'sala-fusca'`, e o id do retry difere do id do request inicial (conferir no stderr do servidor o par `tools/call`).
- [ ] 4.3 Implementar a recusa: `continuar(task, 'recusar')` traduz para `action=decline` e devolve `completado` com `reservado=false` e `motivo`. **Verificação:** continuar uma pausa com `escolha='recusar'` devolve `completado` com `reservado == False` e nenhuma reserva criada.
